# 適用情況

用 Dify Console API 對工作流程做測試時：
- 草稿執行（預覽）：`POST /console/api/apps/{app_id}/advanced-chat/workflows/draft/run`
- 單節點試跑：`POST /console/api/apps/{app_id}/workflows/draft/nodes/{node_id}/run`
- 讀取運行紀錄：`workflow-runs`、`node-executions`、`chat-messages`

# 為什麼要控制

- 測試版和正式版通常共用同一台 Dify 與同一批自架 LLM。
- 一次完整執行可能呼叫 4～8 次 LLM、用掉 1～2 萬 tokens，耗時 15～30 秒。
  這段時間模型在處理測試，正式使用者的請求要排隊。
- 自架模型能同時處理的請求數有限，不會像雲端服務自動擴充。
- 用戶端逾時或中斷後，Dify 通常仍在背景把流程跑完，負載不會因為中斷而消失。

# 規則

1. **一次只送一題**：等上一題完整結束（收到 workflow_finished）才送下一題。
   絕不同時跑兩個測試迴圈，也不平行送出請求。
2. **小批次**：一批最多 5 題，批次之間留空檔。
3. **能用單節點就不用完整流程**：只驗證某個提示詞或 code 節點時，用單節點試跑，
   只呼叫 1 次 LLM。注意單節點試跑會覆蓋該節點的「上次運行」紀錄，要在報告中註明。
4. **先探測再開始**：開始一批測試前，先送一題短問題（例如「你好」）。
   排隊或回應超過約 30 秒，就暫停測試並告知使用者伺服器忙，不要繼續堆請求。
5. **讀紀錄要循序、少量**：讀運行紀錄一次一個請求，不開多條平行連線；
   只讀需要的那幾筆，不整批掃描幾百筆。
6. **避開尖峰**：大批測試盡量排在下班或使用者少的時段；
   不確定時先問使用者現在能不能測。
7. **使用者說先不要測試時**：只讀檔案，不呼叫任何 Dify API。

# 可以建議使用者的設定

- 請 Dify 管理員限制測試應用的同時請求數
  （Dify 有每個應用的同時請求上限設定，例如環境變數 `APP_MAX_ACTIVE_REQUESTS`，實際名稱以部署版本為準）。
- 讓測試應用接另一組模型端點，測試就不會影響正式版。

# 回報

每批測試結束後，在紀錄中寫下：送出幾題、是否有排隊（實際耗時與流程耗時的差距）、
是否有中斷或逾時的請求。
